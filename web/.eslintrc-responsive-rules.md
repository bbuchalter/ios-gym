# Custom ESLint Rules for Tailwind Responsive Design

## Overview

This project includes custom ESLint rules that enforce Tailwind CSS responsive design best practices. These rules are defined in `eslint-local-rules.js` and integrated into the ESLint configuration.

## Rules

### 1. `local/no-excessive-breakpoints` (error)

**Purpose:** Prevent using more than 2 responsive breakpoints for the same CSS property.

**What it checks:**
- Padding/margins: `p`, `px`, `py`, `pt`, `pb`, `pl`, `pr`, `m`, `mx`, `my`, `mt`, `mb`, `ml`, `mr`
- Spacing: `gap`, `space`
- Typography: `text`
- Sizing: `w`, `h`, `min-w`, `max-w`

**Examples:**

```tsx
// ❌ ERROR: Too many breakpoints
<div className="p-2 sm:p-3 md:p-4 lg:p-6">

// ❌ ERROR: Too many text size breakpoints
<h1 className="text-sm sm:text-base md:text-lg lg:text-xl">

// ✅ OK: Single value
<div className="p-4">

// ✅ OK: One breakpoint
<h1 className="text-2xl lg:text-3xl">

// ✅ OK: Two breakpoints (max allowed)
<div className="p-4 md:p-6 lg:p-8">
```

### 2. `local/prefer-mobile-first` (warning)

**Purpose:** Warn about common anti-patterns that indicate over-complication.

**What it checks:**
- Complex text sizing patterns: `text-X sm:text-Y md:text-Z`
- Complex padding patterns: `p-X sm:p-Y md:p-Z`

**Examples:**

```tsx
// ⚠️ WARNING: Complex pattern detected
<div className="px-2 sm:px-4 md:px-6 lg:px-8">

// ⚠️ WARNING: Complex text sizing
<p className="text-sm sm:text-base md:text-lg">

// ✅ OK: Simple pattern
<div className="px-4">

// ✅ OK: One breakpoint
<p className="text-base lg:text-lg">
```

## How It Works

The rules analyze the `className` attribute in JSX elements:

1. **Parse class names** - Split the className string into individual classes
2. **Group by property** - Group classes like `p-4`, `sm:p-6`, `md:p-8` together
3. **Count breakpoints** - Track how many responsive variants exist for each property
4. **Report violations** - Flag patterns that exceed thresholds

## Configuration

The rules are configured in `eslint.config.mjs`:

```javascript
{
  plugins: {
    'local': {
      rules: localRules,
    },
  },
  rules: {
    'local/no-excessive-breakpoints': 'error',      // Blocks builds
    'local/prefer-mobile-first': 'warn',            // Warnings only
  },
}
```

## Running the Rules

```bash
# Run all ESLint rules
npm run lint

# Run only responsive design rules
npm run lint:responsive

# Check specific file
npm run lint -- components/MyComponent.tsx

# Auto-fix issues (if possible)
npm run lint -- --fix
```

## Disabling Rules

If you have a legitimate reason to bypass these rules, add an ESLint comment:

```tsx
{/* eslint-disable-next-line local/no-excessive-breakpoints */}
<div className="p-1 sm:p-2 md:p-3 lg:p-4 xl:p-6">
  Special case requiring many breakpoints
</div>
```

## Customizing Thresholds

To adjust the thresholds, edit `eslint-local-rules.js`:

```javascript
// Current thresholds
if (data.breakpoints.size > 2) {  // Max 2 breakpoints
  // ...
}

if (data.total > 3) {  // Max 3 total declarations
  // ...
}
```

## Testing the Rules

To verify the rules are working, create a test file with known violations:

```tsx
// test-violations.tsx
export function TestComponent() {
  return (
    <div className="p-2 sm:p-3 md:p-4 lg:p-6">
      This should trigger an error
    </div>
  );
}
```

Run: `npm run lint -- test-violations.tsx`

Expected output:
```
✖ Too many breakpoints for "p". Use at most 1-2 breakpoints...
```

## Philosophy

These rules enforce the principle: **Rely on Tailwind's natural responsive behavior** instead of adding multiple breakpoints for every property.

- Tailwind's rem-based spacing scales with user preferences
- Single values work well across most viewport sizes
- Breakpoints should be reserved for major layout changes
- Over-specification makes code harder to maintain

For more details, see [TAILWIND_RESPONSIVE_GUIDELINES.md](./TAILWIND_RESPONSIVE_GUIDELINES.md).
