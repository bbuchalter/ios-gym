# Claude AI Instructions

## Git Commit Policy

### ❌ NEVER Use `--no-verify`

**NEVER bypass Git hooks with `--no-verify` or `--no-gpg-sign` flags.**

When pre-commit or pre-push hooks fail:
1. ✅ **READ the error message carefully**
2. ✅ **FIX the underlying issue** (tests, build, dependencies)
3. ✅ **RUN the checks manually** to verify the fix
4. ✅ **COMMIT normally** once all checks pass

### Why This Matters

Git hooks exist to:
- Catch errors before they reach the repository
- Maintain code quality and test coverage
- Prevent broken builds from being committed
- Ensure consistency across the team

Bypassing hooks means:
- ❌ Broken code enters the repository
- ❌ CI/CD pipelines fail
- ❌ Other developers pull broken code
- ❌ Test coverage decreases
- ❌ Technical debt accumulates

### Pre-Commit Hook Failures

When you see:
```
🔍 Running pre-commit checks...
📦 Building TypeScript...
✓ Build successful
🧪 Running tests...
✗ Tests failed!
```

**DO THIS:**
1. Run `npm test` to see full test output
2. Fix the failing tests or broken code
3. Run `npm run build` to verify build works
4. Commit again (hooks will pass now)

**DON'T DO THIS:**
```bash
git commit --no-verify   # ❌ NEVER DO THIS
```

### Dependency Issues

If you see dependency errors like:
```
Error: Cannot find module '@jest/test-sequencer'
```

**FIX IT:**
```bash
# Reinstall dependencies
npm install

# Or if node_modules is corrupted
rm -rf node_modules package-lock.json
npm install

# Then commit normally
git commit -m "your message"
```

### When Hooks Are Actually Broken

If the hook script itself is broken (not the code):
1. **Report it to the user** - don't bypass it
2. **Ask permission** to fix the hook
3. **Fix the hook script** in `.git/hooks/pre-commit`
4. **Document the fix** in commit message

## Important Project Rules

### DO NOT Modify Generated Files
**NEVER modify files in the `public/` directory directly!**

The `public/` directory contains generated/compiled files. Always modify the source files instead:

- **Source directories:**
  - `client/` - TypeScript source files for client-side code
  - `src/` - TypeScript source files for shared code
  
- **Build process:**
  - Run `npm run build` to compile TypeScript to JavaScript
  - Command: `tsc -p tsconfig.client.json && node fix-imports.js`
  - Output: `public/` directory

### YAML to JSON Conversion
**After modifying `commands.yaml`, always regenerate `web/public/commands.json`!**

- **Source file:** `commands.yaml` - CLI command definitions
- **Generated file:** `web/public/commands.json` - Used by web interface
- **Conversion command:** `npm run convert:yaml`

**Workflow when editing commands.yaml:**
1. Edit `commands.yaml` to modify CLI commands, modes, or grammar
2. Run `npm run convert:yaml` to regenerate the JSON file
3. The web interface will now use the updated commands

**NEVER edit `web/public/commands.json` directly** - it will be overwritten by the conversion script.

### Workflow

#### Option 1: Manual Build
1. Modify TypeScript source files in `client/` or `src/`
2. Run `npm run build` to generate JavaScript in `public/`
3. Test the changes in the browser

#### Option 2: Watch Mode (Recommended for Development)
1. Run `npm run watch` in a terminal
2. Modify TypeScript source files in `client/` or `src/`
3. Watch mode automatically rebuilds on every save
4. Refresh browser to see changes (or use live-reload server)

**Watch Mode Features:**
- Automatically compiles TypeScript when files change
- Runs import fixer after each compilation
- Shows build status with emojis (🔨 building, ✅ success, ❌ error)
- Debounced to avoid multiple rebuilds

### Source File Mappings
- `client/*.ts` → `public/*.js`
- `client/cli/*.ts` → `public/cli/*.js`
- `src/cli/*.ts` → `public/src/cli/*.js`
- `src/exercise/*.ts` → `public/src/exercise/*.js`

### Exceptions - Standalone JavaScript Files in public/
Some files in `public/` are NOT generated and can be modified directly:
- `public/learn.js` - Integrated learning experience (standalone JS)
- `public/learn.html` - Comprehensive course HTML (standalone)
- `public/tutorial.js` - Tutorial functionality (standalone JS)

These are source files that live in `public/` by design.

### How to Tell if a File is Generated
1. Check if there's a corresponding `.ts` file in `client/` or `src/`
2. If yes → it's generated, modify the `.ts` source file
3. If no → it's a standalone file, can be modified directly

**When in doubt, check for the `.ts` source file first!**
